Duas peças: o projeto e a esteira

10 min
OndeO que é
rvnovaes/simple_ppg_managereste projeto — Django + SvelteKit + Postgres + Nginx
rvnovaes/helton (em /opt/helton)a esteira — o kit que instala o loop autônomo em qualquer projeto

A esteira é genérica de propósito. Tudo que ela sabe deste projeto está em dois arquivos versionados aqui: scripts/obra/obra.conf (serviços, portas, como instalar dependências, como migrar e semear) e .env.worktree (o overlay de ambiente por canteiro). Instalar em outro repositório é rodar /opt/helton/scripts/instalar-esteira.sh /caminho/do/projeto — ele copia as peças e para com uma lista de pendências no que depende do domínio, em vez de inventar configuração.

Curiosidade com valor prático: o loop veio do projeto open-source ralph (snarktank/ralph) e foi renomeado para helton — se você encontrar "ralph" em algum link, é a referência ao projeto de origem, não a uma peça nossa.

2

O CLAUDE.md é para humanos e agentes

10 min

Você leu o CLAUDE.md na aula 1 como "o guia do projeto". Agora o segundo sentido do nome: é o arquivo que todo agente de código lê antes de trabalhar — o Claude Code interativo a cada sessão, e o Helton a cada iteração. Ele é o mesmo documento para os dois públicos de propósito: uma regra só, válida para quem quer que esteja digitando.

E aqui as decisões "fechadas" das aulas anteriores mostram sua segunda utilidade: stack decidida, camadas fixas, make ready como verificação única e anti-padrões listados não servem só para humanos iniciantes — servem para restringir o espaço de erro do agente. Um agente com liberdade de escolher ORM, camada e padrão de auth erra de formas criativas; um agente com o CLAUDE.md deste projeto tem um trilho. É a mesma filosofia de "menos decisões em aberto", agora aplicada a quem não dorme.

3

Claude Code interativo: o par de programação

15 min

O uso do dia a dia: abrir claude na raiz do projeto e trabalhar em conversa. Na primeira vez em cada máquina, aceite o diálogo de confiança do workspace — sem isso as permissões do .claude/settings.json são descartadas com aviso.

As práticas da casa, na ordem em que importam:

  • Tarefa grande começa em plan mode. Peça o plano, julgue o plano (arquivos certos? premissas explícitas?), só então deixe executar. Julgar plano é mais barato que julgar diff.
  • O diff é seu. O agente propõe; quem commita assina. Revise como revisaria PR de colega — com atenção especial a migração (regra da aula 2: ler o arquivo gerado) e a qualquer coisa na lista de gates do bloco 7.
  • make ready decide, não a conversa. "Parece pronto" não existe; verde ou não está pronto. É o mesmo critério para humano e agente — e é por isso que enfraquecer a verificação é gate (bloco 7).
  • Contexto explícito rende mais. Aponte o arquivo, a seção do CLAUDE.md, o ADR. O agente que leu apps/people/ como referência produz código no padrão; o que não leu produz Django genérico.
4

O disco é o contrato

10 min

O princípio que organiza a esteira inteira, direto do plans/README.md: o disco é o contrato, o contexto não é. Uma fatia de trabalho atravessa quatro sessões frias — nenhuma herda a memória da anterior:

/grill-me        # sessão 1: a entrevista extrai a spec → specs/<tema>.md
plan mode        # sessão 2, NOVA: "leia specs/<tema>.md e faça o plano" → plans/<nome>.md
/cronograma      # sessão 3, na worktree: plano → scripts/helton/prd.json
helton.sh        # sessão 4..n: cada iteração zera o contexto e relê prd.json + progress.txt

Por que a sessão do plano tem de ser nova, e não continuação do grill: plano nascido na mesma sessão herda a conversa inteira — inclusive o que foi dito e não foi parar na spec. Ele sai bom, a spec segue furada, e o buraco só aparece lá adiante, quando o /cronograma traduz mal alguma coisa. Lendo de uma sessão fria, a spec é submetida ao mesmo teste que tudo o mais: se não se sustenta sozinha, é melhor descobrir no plan mode, onde custa uma pergunta.

5

O ciclo completo da esteira

15 min
/grill-me                                  # extrai a spec        → specs/<tema>.md
sessão NOVA em plan mode                   # o plano              → plans/<nome>.md
                                           # commit e PUSH: a guarda procura o plano no origin
/compatibilizar                            # só com mais de um plano → plans/manifest.json
./scripts/obra/montar-canteiro.sh <nome>   # cria a worktree, sobe a stack, migra e semeia
  ── dentro da worktree ──
  /cronograma                              # converte o plano     → scripts/helton/prd.json
  ./scripts/helton/helton.sh --tool claude 1    # ensaio VIGIADO, uma iteração
  ./scripts/helton/helton.sh --tool claude 30   # AFK
  ── de volta ──
./scripts/obra/desmontar-canteiro.sh <nome>    # preserva a branch helton/<nome>
git merge --no-ff helton/<nome>
./scripts/obra/arquivar-plano.sh <nome>        # move o plano para history/

Três paradas obrigatórias nesse fluxo:

  • O ensaio vigiado (… 1) vem antes do cap real. Uma iteração assistida prova que o cronograma faz sentido antes de você sair de perto.
  • O merge é à mão, e é humano. A esteira entrega uma branch; quem a traz para o tronco é você, revisando com o índice que o desmonte imprime.
  • O arquivar-plano.sh não é opcional. Plano entregue que fica em plans/ volta a ser montado: depois do merge, nenhuma das guardas do --todos dispara, e o loop refaz do zero o que já está no tronco. O script recusa arquivar antes do merge — na ordem certa, nada disso morde.
6

Canteiros: a infra da aula 1 pagando dividendos

10 min

Canteiro é o termo dos scripts para uma git worktree — um checkout paralelo do repositório em outra pasta — com stack Docker própria: projeto Compose próprio, banco próprio, faixa de portas própria, definidos pelo .env que o montar-canteiro.sh gera a partir do .env.worktree.

Agora as decisões esquisitas da aula 1 fecham o círculo: as portas parametrizadas (NGINX_PORT, DB_PORT) existem para N canteiros não disputarem a 8080; e o Vite dentro do Compose existe porque, quando ele rodava no host, os N nginx dos canteiros apontavam todos para o mesmo Vite — cada canteiro exibia o front de outra worktree, sem nenhum erro na tela. A infra foi desenhada para que agentes trabalhem em paralelo sem pisar um no outro — nem em você.

7

Human gates: o que o loop nunca decide

10 min

A seção "Human gates" do CLAUDE.md lista o que um loop autônomo não decide sozinho neste repositório. O critério é um só — reversibilidade: se der errado e só for notado uma semana depois, dá para voltar ao estado anterior usando apenas o git? Não → gate. Na dúvida → gate. As sete categorias:

  1. Decisão sobre a vida acadêmica de alguém — fechar ciclo, classificar candidato, deferir matrícula: o git não desfaz o e-mail que a secretaria mandou. Inclui os anexos de media/, fora do versionamento.
  2. Migrations — tocam dado real; e a major do Postgres invalida o volume (aula 1).
  3. Regra de classificação e contagem de vaga — teste verde não prova critério certo.
  4. Permissões, tenant e autenticação — vazamento entre programas não aparece em lint; é por isso que o seed cria dois programas.
  5. Contrato de API publicado — quebra o typecheck de todo o front (aula 3).
  6. Infra e segredos — compose, nginx, .env*, settings de produção, ADRs.
  7. Enfraquecer a maquinaria de verificação — apagar asserção, afrouxar lint, tirar passo do make ready. Estender a verificação nunca é gate: é o resultado desejado.

Os gates valem para humanos também. A lista não é "coisas que o robô não pode": é o mapa do que, neste sistema, machuca gente ou não volta atrás. No fluxo autônomo ela vira trava de código (o filtro no prompt do loop barra as stories marcadas); no interativo, ela é o seu checklist de "isso eu reviso em dobro".

Armadilhas, exercício e leitura

restante

Armadilhas específicas da esteira

O .gitignore engolindo o .env.worktree. A regra .env.* o pegaria; existe um !.env.worktree logo abaixo. Sem ele, todo canteiro nasce sem overlay — e o git não acusa nada.

CSRF_TRUSTED_ORIGINS e DATABASE_URL precisam estar no overlay. Sem o primeiro, todo canteiro rejeita o próprio login com 403 (o diagnóstico 1 da aula 4). Sem o segundo, o teste do canteiro valida o schema do banco do checkout principal — ou escreve nele.

Instalação no canteiro é npm ci e uv sync --locked. As variantes sem trava sujam a árvore, e o primeiro commit do loop usa git add -A — o ruído entraria no histórico.

Exercício guiado

Um ciclo completo em miniatura, em dupla, com uma fatia pequena e sem gate (um texto de tela, um empty state): /grill-me → plano em sessão nova → montar-canteiro.sh → /cronograma → uma iteração vigiada do helton.sh, lendo juntos o que o loop fez → desmontar, revisar o diff, mergear, arquivar o plano. O objetivo não é a fatia: é ver cada guarda disparar no lugar certo.

Leitura de casa

  • manual_dev.md — inteiro, agora com repertório para entendê-lo todo.
  • plans/README.md — o contrato da esteira, com o porquê de cada guarda.
  • scripts/obra/obra.conf — leia os comentários: é a esteira explicando o que precisou saber deste projeto.
  • scripts/helton/CLAUDE.md — ler (não editar!): é instrutivo ver o que o loop é instruído a fazer a cada iteração.
