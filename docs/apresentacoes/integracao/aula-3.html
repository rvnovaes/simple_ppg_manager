1

O contrato: onde o backend termina

15 min

Antes de entrar no Svelte, fechamos a conta da aula 2. A impressão que fica de lá está certa: o Django Ninja é mesmo uma camada fina sobre o Django puro. Tudo de substância — model, QuerySet, auth, transação — é Django; o Ninja só traduz HTTP ↔ Python. O que resta dele para conhecer cabe num arquivo, o backend/api.py:

api = NinjaAPI(
    title="PPGD Manager API", version="1.0.0",
    auth=django_auth,   # sessão do Django é o PADRÃO de toda rota (ADR-003);
)                       # rota pública declara auth=None e justifica com "# público"

@api.exception_handler(DomainError)      # todo erro de negócio vira 4xx com
def on_domain_error(request, exc):       # corpo padronizado {detail, code} —
    ...                                  # é POR ISSO que router não faz try/except

api.add_router("/auth/", accounts_router)    # cada app pluga seu router;
api.add_router("/people/", people_router)    # o "/api/v1" vem do config/urls.py

Três coisas para registrar, e o Ninja está encerrado:

  • Auth por padrão, exceção explícita. O auth=django_auth na raiz faz toda rota exigir sessão (e checar CSRF nas escritas) sem que cada router precise lembrar disso. O caminho seguro é o caminho sem esforço.
  • Erros têm um formato só. Os exception handlers centrais convertem DomainError, autenticação ausente e payload inválido em {detail, code}. O front confia nesse formato — você vai ver mensagemDeErro() e codigoDeErro() no bloco 6 lendo exatamente esses campos.
  • O OpenAPI é o produto. Como entrada e saída são schemas Pydantic, o Ninja descreve a API inteira em um documento OpenAPI, de graça. É dele que nasce a metade tipada do front.

E é este o gancho da aula: o comando make gen-api exporta esse OpenAPI para frontend/src/lib/api/openapi.json e gera schema.d.ts — um arquivo TypeScript com o tipo de cada rota, parâmetro e resposta. A partir daí, o contrato entre back e front não é combinado verbal: é código que o svelte-check verifica.

Regra da casa: schema.d.ts e openapi.json são gerados — PR que os edita à mão é recusado. E mudou schema ou rota sem rodar make gen-api? O svelte-check de quem só mexeu no front quebra sem entender o porquê.

2

SvelteKit: rotas são pastas

15 min

O Svelte é a linguagem de componentes; o SvelteKit é o framework em volta — roteamento, build, convenções de arquivo. A regra central: a URL é o caminho da pasta dentro de src/routes/, e arquivos com prefixo + têm papel especial:

src/routes/
  +layout.ts              # export const ssr = false → SPA pura (ADR-005)
  +layout.svelte          # casca de TODAS as páginas
  (auth)/login/+page.svelte      # /login
  (app)/                         # grupo: layout com menu + guarda de sessão
    +layout.svelte
    pessoas/[vinculo]/+page.svelte        # /pessoas/candidatos, /pessoas/administrativo
    pessoas/[vinculo]/[id]/+page.svelte   # /pessoas/administrativo/42
    professores/+page.svelte              # /professores
  • +page.svelte é a tela; +layout.svelte é a moldura que envolve as telas abaixo dela (e layouts aninham).
  • (app) e (auth) são grupos: os parênteses agrupam rotas sob um layout comum sem aparecer na URL. É assim que todas as telas internas ganham o menu e a guarda de sessão de uma vez, e o login fica fora delas.
  • [vinculo] é parâmetro dinâmico: a mesma tela atende /pessoas/candidatos e /pessoas/administrativo, lendo o valor em page.params.vinculo.
  • Navegação por código usa goto(), e links usam resolve() — nunca string montada à mão.

E o que não existe aqui, por decisão: +page.server.ts e funções load com acesso a banco. Isso é o mundo SSR do SvelteKit — nosso ssr = false no layout raiz desliga tudo (ADR-005). Toda busca de dado acontece no navegador, via API, depois que a página carrega. O build (adapter-static) gera arquivos estáticos com fallback: index.html: qualquer URL cai no mesmo HTML, e o roteador da SPA decide o que mostrar — é por isso que o Nginx de produção tem o try_files … /index.html que vimos na aula 1.

3

Svelte: o componente

15 min

Um arquivo .svelte é um componente: lógica, marcação e (opcionalmente) estilo, juntos. Diferente do React, o Svelte é um compilador — o template vira código imperativo eficiente no build, não há re-render de árvore inteira.

<script lang="ts">
  // a lógica: imports, estado, funções
  let { children } = $props();      // props que o componente recebe
</script>

<h1>Olá</h1>                         <!-- a marcação: HTML de verdade -->
{#if sessao.usuario}                 <!-- controle de fluxo no template -->
  {#each pessoas as pessoa (pessoa.id)}   <!-- a chave (id) preserva o DOM -->
    <li>{pessoa.full_name}</li>
  {/each}
{:else}
  <p>Carregando…</p>
{/if}

{@render children()}                 <!-- layout renderiza a página filha aqui -->

O essencial da sintaxe: {expressão} interpola; {#if}/{#each}/{:else} controlam fluxo; eventos são atributos (onclick={arquivar}); e {@render children()} é como um layout diz "a página entra aqui". Atributos dinâmicos seguem o HTML: disabled={condição}, class:opacity-55={condição} liga uma classe a um booleano.

E o CSS?

O projeto usa Tailwind v4: classes utilitárias direto na marcação (class="flex items-center gap-4"), com os tokens do projeto (bg-papel, text-grafite, border-borda) definidos no app.css. Classes recorrentes com nome de domínio — etiqueta, botao-icone, aviso-erro — também moram lá. Sem CSS-in-JS.

4

Runas: reatividade explícita

20 min

Reatividade é a pergunta central de todo framework de front: quando o dado muda, quem reexecuta? No Svelte 5 a resposta são as runas — marcadores que o compilador entende (por isso o $ no nome; não são funções que existem em runtime). São quatro no dia a dia, e a tela de pessoas usa todas:

$state — o dado que muda

let pessoas = $state<Pessoa[]>([]);
let carregando = $state(true);
let erro = $state('');
let arquivando = $state<number | null>(null);  // id da pessoa em operação

Uma variável $state é observada: qualquer trecho do template que a lê se atualiza sozinho quando ela muda — e só ele. Atribuir é o bastante (carregando = false); não há setState. Repare no padrão dos quatro estados: dado, carregando, erro, operação-em-curso. Quase toda tela do projeto tem esse quarteto.

$derived — o dado calculado

const slug = $derived(page.params.vinculo ?? '');   // segue a URL
const recorte = $derived(RECORTES[slug]);           // segue o slug
const podeArquivar = $derived(sessao.pode('people.change_person'));

$derived declara um valor que depende de outros: quando page.params muda (a pessoa navegou de "candidatos" para "administrativo"), slug e recorte recalculam em cascata, e o template atrás deles também. Você nunca escreve "atualize X quando Y mudar" — declara a fórmula e o compilador descobre as dependências.

$effect — o ponto de contato com o mundo

$effect(() => {
  if (recorte) carregar(recorte.bond);   // mudou o recorte → busca de novo
});

$effect roda uma função sempre que algo que ela lê muda. É a ponte para fora da reatividade: buscar na API, redirecionar, mexer no DOM. Regra de bom senso que o projeto segue: efeito é para efeito colateral — se você está usando $effect para calcular um valor e guardar num $state, o certo era um $derived.

$props — o que vem de fora

let { children } = $props();   // num layout: a página filha
// num componente: let { nome, tamanho = 16 } = $props();

Declara o que o componente recebe de quem o usa, com desestruturação e defaults do próprio JavaScript.

Sintaxe legada é proibida para estado local. Tutoriais antigos de Svelte ensinam let reativo "mágico", $: e stores com writable(). Este projeto é Svelte 5 com runas — a reatividade é explícita e funciona em qualquer arquivo, não só dentro de componente. Se o tutorial que você achou usa $:, ele é de outra era; a referência certa é svelte.dev/docs.

5

Estado global: a sessão

15 min

Runas não vivem só em componente: um arquivo .svelte.ts também é compilado, e é assim que o projeto tem estado global sem biblioteca nenhuma. O exemplo canônico é lib/sessao.svelte.ts — quem está logado, para toda a SPA:

class Sessao {
  usuario = $state<Usuario | null>(null);   // reflexo, em memória, do cookie
  carregando = $state(true);                // de sessão — a VERDADE mora no Django

  pode(permissao: string): boolean {        // ex.: sessao.pode('people.view_person')
    return this.usuario?.permissions.includes(permissao) ?? false;
  }

  async entrar(username, password) {
    await garantirCsrf();                 // planta o cookie csrftoken antes
    const { data, error } = await api.POST('/auth/login', { body: {...} });
    ...
    this.usuario = data;                    // TODO template que lê `usuario`
  }                                         // atualiza sozinho: menu, guarda, tudo
}
export const sessao = new Sessao();        // instância única, importada por todos

Repare no comentário do próprio arquivo: a verdade sobre quem está logado mora no cookie de sessão do Django — esta classe é só o reflexo dela em memória, para as telas não perguntarem ao servidor a cada render. O tipo Usuario vem do contrato (components['schemas']['UserOut']): se o backend mudar o formato do usuário, este arquivo quebra no svelte-check, não em produção.

Quem consome a sessão é o layout do grupo (app) — a guarda das telas internas:

$effect(() => {                            // sem sessão → volta para o login.
  if (sessao.usuario === null && !sessao.carregando) {
    goto(resolve('/login'), { replaceState: true });
  }
});
6

O cliente de API

15 min

Toda chamada de rede do front passa por um arquivo: lib/api/client.ts. fetch cru nas telas é proibido (Seção 8 do CLAUDE.md) — e o motivo fica óbvio lendo o que o cliente resolve de uma vez por todas:

export const api = createClient<paths>({   // <paths> vem do schema.d.ts GERADO:
  baseUrl: '/api/v1',    // RELATIVA, sempre — URL absoluta quebra a origem única (ADR-004)
  credentials: 'include' // sem isto o cookie de sessão não acompanha a requisição
});

api.use(csrf);           // middleware: em todo POST/PUT/PATCH/DELETE, lê o cookie
                         // `csrftoken` e envia o header X-CSRFToken. NENHUMA tela
                         // pensa em CSRF — o preço do ADR-003, pago uma vez, foi aqui.

O createClient<paths> é o openapi-fetch tipado pelo contrato do bloco 1. O efeito prático é que o TypeScript conhece a API inteira:

  • api.GET('/people/', { params: { query: { bond } } }) — a URL é autocompletada, e bond só aceita os quatro valores do enum PersonBond que vimos no schemas.py da aula 2.
  • A resposta sai tipada como PersonOut[] paginado. Errar o nome de um campo é erro de compilação, não surpresa em produção.
  • O retorno é sempre { data, error } — sem exceção para capturar; a tela decide o que fazer com cada um.

Os helpers ao redor completam o kit: garantirCsrf() planta o cookie antes da primeira escrita (no login ainda não há sessão); mensagemDeErro(erro) extrai o detail padronizado pelos exception handlers do bloco 1; e codigoDeErro(erro) extrai o code estável. A distinção importa: a mensagem é para a pessoa ler; o código é para a tela decidir — comparar o texto do detail seria acoplar a lógica à redação da mensagem.

7

Uma tela de verdade, de cima a baixo

20 min

Agora tudo junto. A tela pessoas/[vinculo]/+page.svelte lista candidatos ou administrativo — é a ponta do endpoint GET /people/?bond=… que dissecamos na aula 2. O esqueleto dela, anotado:

// 1. TIPOS DO CONTRATO — nada de interface duplicada à mão
type Pessoa = components['schemas']['PersonOut'];

// 2. A URL COMANDA — derivados seguem o parâmetro da rota
const slug = $derived(page.params.vinculo ?? '');
const recorte = $derived(RECORTES[slug]);   // slug pt na URL → bond do contrato;
                                            // os dois idiomas não se misturam
// 3. O QUARTETO DE ESTADO
let pessoas = $state<Pessoa[]>([]);
let carregando = $state(true);
let erro = $state('');
let arquivando = $state<number | null>(null);

// 4. BUSCAR QUANDO A URL MUDAR
$effect(() => { if (recorte) carregar(recorte.bond); });

// 5. ESCREVER: chama a API, atualiza a lista com a RESPOSTA do servidor
async function arquivar(pessoa: Pessoa) {
  arquivando = pessoa.id;                    // desabilita SÓ este botão
  const { data, error } = await api.POST('/people/{person_id}/archive',
    { params: { path: { person_id: pessoa.id } } });
  arquivando = null;
  if (error || !data) { erro = mensagemDeErro(error, '…'); return; }
  pessoas = pessoas.map((p) => (p.id === data.id ? data : p));
}                                            // ↑ a linha nova vem do backend, que é
                                             // quem sabe o estado real após archive()

E no template, os três estados sempre presentes — carregando, vazio (com texto que explica de onde a lista vem), e a lista em si:

{#if carregando}
  <p class="etiqueta">Carregando…</p>
{:else if pessoas.length === 0}
  <p>{recorte.vazio}</p>                <!-- vazio explicado, nunca tela em branco -->
{:else}
  {#each pessoas as pessoa (pessoa.id)}
    ...
    {#if podeArquivar}                  <!-- botão só para quem tem a permissão -->
      <button
        disabled={pessoa.status === 'archived' || arquivando === pessoa.id}
        onclick={() => arquivar(pessoa)}>…</button>
    {/if}
  {/each}
{/if}

Dois detalhes de produto que valem imitar: arquivar é o "excluir" desta tela — a pessoa não some do banco, porque continua sendo quem assinou o que assinou (o invariante do archive() da aula 2); e o botão de pessoa arquivada fica desabilitado em vez de sumir — sumir daria a impressão de que a ação não existe.

O espelho dos cinco passos. Na aula 2, decoramos o esqueleto da rota de escrita (permissão → busca escopada → transação → método do model → auditoria). Este é o esqueleto gêmeo do lado de cá: tipos do contrato → derivados da URL → quarteto de estado → efeito que busca → escrita que confia na resposta. Toda tela nova do projeto é uma variação disso.

8

Permissão na tela é cortesia

10 min

O menu do layout (app) é uma aula de autorização em UI. Cada item é condicional — link que só leva a 403 é pior do que link ausente — e a escolha do critério é deliberada, item a item:

{#if sessao.pode('people.view_person')}        <!-- por PERMISSÃO: é o que a
  <a href={resolve('/pessoas/administrativo')}>…  tela de destino exige -->
{/if}

{#if sessao.temPapel('Candidato')}             <!-- por PAPEL: os quatro papéis têm
  <a href={resolve('/acompanhamento')}>…       a mesma view_*, e o que muda é o
{/if}                                          recorte que o backend aplica -->

A regra: pode() (permissão) é o critério padrão — é o mesmo nome que o require_perm checa no backend. temPapel() (Group) só entra quando a permissão não distingue o público, e o comentário no código explica o porquê caso a caso. Até a rota inicial pós-login é decidida por permissão: o Candidato da isolada não tem people.view_person, então jogá-lo em /pessoas seria abrir a sessão com um 403 na cara.

Mas nada disso é segurança. Esconder botão e menu é cortesia de UX. Quem protege é o backend: o require_perm na primeira linha de cada rota e o escopo de current_program rodam sempre, inclusive para quem chamar a API por fora da tela. O mesmo vale para validação de formulário: a do front é conforto; a que vale é a do schema Ninja. Nunca confie só no front.

Exercício e leitura de casa

restante

Exercício guiado: quebrar o contrato de propósito

Numa branch descartável, para sentir a maquinaria trabalhando a seu favor:

  1. Renomeie phone_number para phone em PersonOut (apps/people/schemas.py) — só no schema de saída.
  2. Rode make gen-api (backend de pé) e depois make typecheck.
  3. Veja o svelte-check apontar cada tela que lia o campo antigo — é o contrato pegando a quebra em segundos, antes de qualquer clique.
  4. Desfaça tudo (git checkout .) e confirme o make ready verde.

Depois, o exercício construtivo: escolha uma tela simples (a listagem de disciplinas, por exemplo) e leia-a inteira identificando o esqueleto do bloco 7 — tipos, derivados, quarteto, efeito, escrita.
