A postura: reproduzir antes de corrigir

10 min

Duas regras vêm antes de qualquer ferramenta. Primeira: não se corrige o que não se reproduziu. Um sintoma que casa com um problema conhecido pode ter outra causa — agir pelo reflexo troca um bug por dois. Segunda, que é da Seção 9 do CLAUDE.md: todo bug corrigido ganha antes um teste que o reproduz. O teste vermelho é a prova de que você entendeu a causa; ele ficando verde é a prova do conserto — e ele fica de guarda para sempre.

Com isso posto, o mapa. Quase todo problema aqui se localiza perguntando "em qual camada da aula 1 ele mora?":

2

Logs: o que cada container conta

10 min
docker compose logs -f backend    # o mais útil: cada request + traceback de 500
docker compose logs -f nginx      # access log: qual rota, qual status, qual upstream
make web                          # atalho para logs -f frontend (o Vite)
docker compose ps                 # quem está de pé, e desde quando

O log do backend é o do runserver: uma linha por requisição ("POST /api/v1/people/ 201") e, num erro 500, o traceback completo do Python — leia-o de baixo para cima: a última linha é o erro, e o primeiro arquivo nosso na pilha (algo em apps/) é onde olhar. Como DEBUG=True em dev, erros de API também voltam com detalhe no corpo da resposta.

O log do nginx responde outra pergunta: a requisição chegou onde eu acho que chegou? Um 502 ali significa "o upstream não respondeu" — o Django ou o Vite caíram; um 404 que não aparece no log do backend nunca saiu do Nginx.

A API sem o front: /api/v1/docs e os códigos de erro

15 min

O Ninja publica de graça uma interface interativa da API inteira: http://localhost:8080/api/v1/docs (o atalho /api redireciona para lá). Cada rota com seus parâmetros e schemas, e o botão Try it out executa de verdade. Como ela vive na mesma origem (aula 1!), sua sessão logada vale ali — dá para isolar "o bug é na tela ou na API?" em um minuto, chamando a rota por fora do front.

Todo erro da API tem o formato {detail, code} dos exception handlers do api.py. A tabela de tradução:

StatusSignificado aquiPara onde olhar
401not_authenticated — sem sessão válidaCookie sessionid presente? Logou por :8080?
403Permissão negada (require_perm) ou CSRF rejeitadoO usuário tem a permissão? O X-CSRFToken foi junto?
404Não existe ou é de outro programaLembre da aula 2: a busca é escopada — id de outro tenant responde 404 de propósito
422validation_error — payload fora do schemaO campo errors aponta campo a campo
4xxDomainError com code próprioRegra de negócio recusou — é comportamento, não bug
500Bug nossoTraceback no log do backend (bloco 2)

O 404 que parece bug. "A pessoa existe no banco, mas a API responde 404" é o escopo de tenant funcionando: a conta logada não pertence ao programa daquele registro. Antes de caçar bug, confira com qual conta você está logado — o CONTAS-DEMO.txt tem contas dos dois programas justamente para esse teste.

4

O shell do Django: o ORM ao vivo

10 min

O shell abre um Python interativo com o projeto carregado — o laboratório para testar uma consulta ou uma regra antes de escrever código (roda no host, contra o banco da 5433, como o make run):

cd backend && uv run python manage.py shell

>>> from apps.people.models import Person
>>> Person.objects.count()
>>> p = Person.objects.filter(primary_email__icontains="demo").first()
>>> Person.objects.for_program(p.program).staff()   # os recortes da aula 2, ao vivo
>>> print(Person.objects.staff().query)             # o SQL que o ORM vai emitir

>>> p2 = Person(full_name="Teste", status=Person.Status.ARCHIVED)
>>> p2.archive()                    # invariante em memória: levanta
InvalidStateTransition: Pessoa já está arquivada.   # InvalidStateTransition — sem tocar o banco

O .query merece destaque: quando uma listagem vem errada, imprimir o SQL do QuerySet mostra na hora se o filtro que você imaginou é o filtro que existe. E note a última parte: dá para exercitar um invariante de model sem salvar nada — é exatamente o que os testes de model fazem.

O banco na mão: psql e a auditoria

10 min

Território de vocês. O Postgres de dev está publicado no host (aula 1: porta 5433, credenciais padrão ppg/ppg):

psql -h localhost -p 5433 -U ppg ppg
ppg=# \dt                          -- as tabelas: people_person, audit_..., auth_...
ppg=# \d people_person             -- colunas, índices e as UniqueConstraints da aula 2
ppg=# select id, full_name, status, program_id from people_person limit 10;

Duas disciplinas ao usar isso: leitura à vontade, escrita jamais — um UPDATE na mão desvia de invariante, permissão e auditoria de uma vez (é o mesmo motivo do Admin trancado, ADR-006; correção excepcional de dado é pelo Admin, que audita). E lembre que schema quem muda é migração, nunca DDL manual.

E a jóia para investigação: o AuditLog. Toda escrita relevante registrou quem, quando, o quê e o alvo — quando o mistério é "quem mudou isso?", a resposta já está gravada. Dá para ler pelo Django Admin (você é sysadmin) ou direto na tabela do app audit.

O navegador: Network, cookies e o typecheck

10 min

Para bug de tela, o DevTools (F12) é o log do front. Na aba Network, filtre por api/ e examine a requisição que falhou:

  • Request: o cookie sessionid foi junto? Nas escritas, o header X-CSRFToken apareceu (é o middleware do client.ts da aula 3 trabalhando)?
  • Response: o corpo {detail, code} diz o motivo — a mesma tabela do bloco 3.
  • Console: erro de JavaScript e os avisos do Svelte aparecem aqui; o log do processo do Vite é o make web.

E o "debugger que roda antes do bug": make typecheck. O svelte-check e o mypy pegam em segundos o desencontro entre o que a tela espera e o que o contrato entrega — inclusive o clássico "mexi em schema e esqueci o make gen-api", que a aula 3 mostrou como provocar de propósito.

Testes como ferramenta de investigação

10 min
make test                                  # a suíte inteira (precisa do banco de pé)
cd backend && uv run pytest apps/people/   # só um app
uv run pytest -k archive -x -vv            # só testes com "archive" no nome;
                                           # -x para no primeiro erro, -vv detalha

O fluxo de caça a bug é: reproduza o sintoma num teste — de model se o invariante falhou, de API (via client do Ninja) se o fluxo falhou —, veja-o vermelho, e só então mexa no código. O teste vira o critério objetivo de "consertei", substituindo o "parece que agora foi" de clicar na tela. Os testes rodam contra Postgres de verdade (paridade com produção, Seção 9); o conftest.py da raiz do backend prepara isso.

Três diagnósticos guiados

15 min

Três defeitos clássicos deste projeto — as armadilhas da aula 1, agora do ponto de vista de quem investiga. Em aula, provocamos cada um de propósito e percorremos o caminho:

1. Login devolve 403. Network mostra o POST /auth/login com 403 e o X-CSRFToken presente — então não é o front. Log do backend acusa rejeição de CSRF. Hipótese: origem não confiada → confira CSRF_TRUSTED_ORIGINS no .env contra a porta real do Nginx. É o defeito que não menciona porta nenhuma na mensagem.

2. Salvei o arquivo e a tela não mudou. Nenhum erro em lugar nenhum — é o pior tipo. Network (aba WS) mostra o WebSocket do HMR tentando a porta errada. Causa: NGINX_PORT divergindo do hmr.clientPort do vite.config.ts. Enquanto isso, F5 manual funciona — o que confirma que só o hot reload morreu.

3. 502 Bad Gateway na raiz. docker compose ps mostra o serviço frontend reiniciando em loop; make web revela o cannot find module de binário glibc — alguém trocou a imagem para -alpine, ou o node_modules do host foi instalado de um jeito exótico. O Nginx está inocente: ele só não tem a quem repassar.
