Onde mora o código

15 min
backend/
  api.py                 # NinjaAPI raiz: versão, auth, exception handlers
  config/                # settings (base/dev/prod), urls, wsgi
  apps/
    core/                # require_perm, current_program, DomainError
    people/  accounts/   # pessoas, usuários e papéis
    programs/  academic/  audit/
frontend/src/
  routes/                # telas (SPA, ssr = false) — assunto da aula 3
  lib/api/client.ts      # openapi-fetch, baseUrl RELATIVA '/api/v1'
  lib/api/schema.d.ts    # GERADO pelo make gen-api — nunca editar à mão

Cada app Django tem models.py, router.py, schemas.py, admin.py e, quando precisa, services.py. A arquitetura tem duas camadas e meia, e cada coisa tem um lugar só:

  • Model = entidade de domínio. Regra de negócio que protege invariante vive em método do próprio model (person.archive()). Testa-se instanciando em memória, sem banco.
  • Router = borda. Valida o schema de entrada, checa permissão com require_perm(...), escopa com current_program(...), chama o model, devolve schema de saída. Nunca contém regra de negócio; nunca serializa model direto.
  • services.py só quando a operação escreve em mais de um model e precisa de transaction.atomic(). Não se cria service "por simetria".
  • Nada além disso. Sem Repository, sem Mapper, sem Unit of Work. O ORM do Django já é essas coisas (ADR-002).

E transversal a tudo: toda escrita relevante gera um AuditLog — quem, quando, o quê, alvo — dentro da mesma transação.

A régua de sanidade

Um campo novo, da tela ao banco, custa ~6 arquivos: model → migração → schemas → admin → make gen-api → tela Svelte. Se um campo simples está exigindo mais que isso, a arquitetura está sendo violada — pare e discuta.

O resto da aula é a leitura guiada do app people, de cima a baixo. Antes, uma frase sobre o Django em si: é um framework "com baterias incluídas" — ORM (acesso a banco), autenticação, permissões, migrações e um admin já vêm prontos, e é por isso que ele carrega a stack sozinho. Um projeto Django (nosso config/) é a configuração; os apps (people, accounts, audit…) são pacotes Python que agrupam o código por assunto. Todos os trechos a seguir são o código real, resumido.

2

Model: uma classe que é uma tabela

15 min

O coração do Django é o ORM (Object-Relational Mapper): você descreve a tabela como uma classe, e o Django traduz Python ↔ SQL. Classe = tabela, atributo = coluna, instância = linha.

class Person(models.Model):          # herdar de Model = virar tabela (people_person)
    class Status(models.TextChoices): # vocabulário fechado para um campo
        ACTIVE = "active", "Ativa"    # (valor no banco, rótulo humano)
        ARCHIVED = "archived", "Arquivada"

    full_name = models.CharField("nome completo", max_length=200)
    primary_email = models.EmailField("e-mail principal")   # valida formato
    phone_number = models.CharField("telefone", max_length=30, blank=True)
    status = models.CharField(max_length=20, choices=Status,
                              default=Status.ACTIVE)
    created_at = models.DateTimeField(auto_now_add=True)  # carimbo técnico,
    updated_at = models.DateTimeField(auto_now=True)      # nunca dado de negócio

Cada tipo de campo (CharField, EmailField, DateTimeField…) sabe seu tipo SQL e sua validação. Detalhe que confunde todo iniciante: blank=True significa "pode vir vazio num formulário" (validação), enquanto null=True significa "a coluna aceita NULL" (banco). Texto opcional usa só blank e guarda ""; relação opcional usa os dois.

Convenções da casa

Nome de model no singular (Person); dinheiro e nota em DecimalField, nunca FloatField; datas sempre com timezone (USE_TZ = True); e auto_now* só para carimbo técnico — data de negócio é campo explícito, preenchido pela regra.

Relações, Meta e constraints

15 min

ForeignKey conta a história do domínio

program = models.ForeignKey(         # toda Person pertence a UM programa —
    "programs.Program",              # a chave de tenant da aula 1
    on_delete=models.PROTECT,        # proíbe apagar programa que tem gente
    related_name="people",           # cria o caminho inverso: programa.people
)
user = models.ForeignKey(            # FK, NÃO OneToOne, de propósito: o User é
    settings.AUTH_USER_MODEL,        # global e a Person é por programa — quem atua
    null=True, blank=True, ...       # em 2 programas tem 1 conta e 2 pessoas.
)                                    # Opcional: egresso não loga, mas existe.

ForeignKey é o "muitos-para-um" (muitas pessoas, um programa). O on_delete é obrigatório e é uma decisão de domínio: PROTECT faz o banco recusar a exclusão do programa enquanto houver pessoas nele — apagar em cascata seria destruir cadastro. O related_name dá o caminho de volta: de um Program, programa.people.all() lista suas pessoas. Existe também o OneToOneField ("um-para-um"): é o vínculo entre Person e TeacherProfile — uma pessoa tem no máximo um perfil docente.

Meta e constraints: o banco é o último guarda

class Meta:
    ordering = ["full_name"]         # ordem padrão de toda listagem
    constraints = [
        models.UniqueConstraint(     # e-mail único DENTRO do programa —
            fields=["program", "primary_email"],  # entre programas repete,
            name="unique_email_por_programa",     # e é o caso multi-tenant
        ),
    ]

A classe interna Meta guarda o que é da tabela, não de uma coluna. A UniqueConstraint vira um índice único no Postgres: mesmo que algum código esqueça de validar, o banco recusa a duplicata. Repare que a unicidade é composta — (program, primary_email) — porque a mesma pessoa pode existir em dois programas: o multi-tenant da aula 1 aparecendo no nível do banco.

Migrações: o schema do banco versionado no git

10 min

Você nunca escreve CREATE TABLE. Mudou o model → make migrations compara as classes com o estado anterior e gera um arquivo Python em migrations/ descrevendo a diferença → make migrate aplica no banco, em ordem, registrando o que já rodou. É assim que o banco de todo mundo (e o de produção) evolui igual.

Duas regras da casa: migração gerada é lida antes do commit (o autogenerate erra — rename vira drop+create, default esquecido trava deploy), e migração já aplicada nunca se edita à mão. E uma regra de deploy que vem da aula 1: a migração roda antes do código novo, então ela precisa ser retrocompatível — campo novo entra null=True ou com default.

Migração também carrega dados, não só schema: os papéis do domínio ("Secretaria", "Coordenação") são Groups criados por data migration — você vai ver isso no bloco 7.

5

QuerySet: consultas escritas em Python

15 min

Person.objects é o manager — a porta de entrada das consultas. Cada chamada devolve um QuerySet, que é preguiçoso (só vira SQL quando alguém itera) e encadeável. O projeto dá nome aos recortes do domínio como métodos de um QuerySet próprio:

class PersonQuerySet(models.QuerySet):
    def for_program(self, program):   # o escopo de tenant, sempre primeiro
        return self.filter(program=program)

    def teachers(self):               # "tem perfil docente": atravessa a
        return self.filter(teacher_profile__isnull=False)  # relação com __

    def staff(self):                  # papel vem do Group do usuário (auth),
        return self.filter(           # não de um campo duplicado em Person
            user__groups__name__in=("Secretaria", "Coordenação")
        ).distinct()

# no model: objects = PersonQuerySet.as_manager()

O __ (dois underscores) navega relações e aplica operadores: teacher_profile__isnull=False é "existe linha ligada na tabela de perfil docente"; user__groups__name__in=… atravessa duas relações até o nome do grupo. E como tudo encadeia, o router compõe: Person.objects.for_program(programa).teachers() — uma frase do domínio que vira um SQL só. Note que os recortes não são exclusivos: o coordenador que dá aula aparece em teachers() e em staff() — por isso vínculo não é um campo "tipo de pessoa" no model.

Regra da Seção 8

Query fora de models.py/managers precisa de justificativa em comentário. O caminho normal é criar o método nomeado no QuerySet e chamá-lo do router — a consulta ganha nome, teste e um lugar só para mudar.

Regra de negócio e a rota de escrita

20 min
def archive(self) -> None:
    # Invariante: arquivar só a partir de ACTIVE. Duas vezes é erro
    # do chamador, não no-op silencioso.
    if self.status == self.Status.ARCHIVED:
        raise InvalidStateTransition("Pessoa já está arquivada.")
    self.status = self.Status.ARCHIVED

É o ADR-002 em uma tela: a regra vive onde o dado vive. O teste disso instancia Person() em memória e chama o método — sem banco, sem mock. A exceção herda de DomainError, e o handler central da API a converte em resposta 4xx padronizada; nenhum router faz try/except de negócio. E veja como a rota que arquiva usa tudo que apareceu até aqui:

@router.post("/{int:person_id}/archive", response=PersonOut)
def archive_person(request, person_id: int):
    require_perm(request, "people.change_person")     # 1. permissão, sempre 1ª linha
    person = get_object_or_404(                        # 2. busca JÁ escopada: pessoa de
        Person.objects.for_program(current_program(request)),  # outro programa = 404
        pk=person_id,
    )
    with transaction.atomic():                     # 3. tudo ou nada
        person.archive()                               # 4. a regra mora no model
        person.save(update_fields=["status", "updated_at"])
        audit.record("people.archive", request=request, target=person)
    return person                                  # 5. sai moldado pelo PersonOut

Dois detalhes de Django aí: get_object_or_404 busca ou responde 404 (e o 404 é deliberado — 403 revelaria que o id existe em outro tenant); transaction.atomic() garante que a mudança de status e o registro de auditoria entram juntos ou nenhum entra. Este esqueleto de cinco passos é o padrão de toda rota de escrita do projeto — decore-o.

E o contrato da borda: a rota recebe PersonIn e devolve PersonOut — schemas Pydantic explícitos em schemas.py. Serializar o model direto faria o contrato da API mudar por acidente quando uma coluna mudasse; com o schema, mudar a API é sempre um ato deliberado. É desse contrato que o front gera seus tipos, como a aula 3 vai mostrar.

Auth e Admin: as baterias incluídas

10 min

Auth de fábrica: User, Group, Permission

O Django já traz as tabelas de usuário, grupo e permissão — e cria sozinho, para cada model, as permissões add/change/delete/view (o "people.add_person" das rotas é isso: app + ação + model). O projeto não inventa RBAC: papel do domínio ("Secretaria", "Coordenação") é um Group com permissões, criado por data migration, e require_perm() é um helper fino sobre o user.has_perm() nativo (ADR-003). Você viu no staff() do bloco 5 que até a listagem de pessoas administrativas sai do Group — uma verdade só.

Admin: o CRUD que vem de graça (e por isso é trancado)

@admin.register(Person)                # registra o model no Admin
class PersonAdmin(AuditedModelAdmin):  # base do projeto: toda escrita audita
    list_display = ("full_name", "primary_email", "program", "status")
    list_filter = ("program", "status")
    search_fields = ("full_name", "primary_email")
    raw_id_fields = ("user",)          # senão vira um <select> com TODOS os usuários
    readonly_fields = ("created_at", "updated_at")

Essas poucas linhas dão uma interface completa de listagem, busca, filtro e edição. É a maior "bateria incluída" do Django — e exatamente por isso é perigosa: editar ali muda o banco por fora dos métodos do model (o archive() nunca roda). Daí o ADR-006: só sysadmin entra, toda escrita audita, e a tela de verdade da secretaria é /pessoas no front.

Última peça: o router.py não é Django "puro" — é Django Ninja, a camada de API da aula 1. Mas repare que ele é fino de propósito: tudo de substância que você leu está no model, no QuerySet e no auth nativo. O Ninja só traduz HTTP ↔ Python, com os schemas como contrato explícito — e é por ele que a aula 3 começa.

8

O ritual de commit

5 min
  • make ready verde antes de qualquer commit — sem exceção.
  • Commits pequenos, mensagem em português, modo imperativo: "adiciona campo phone_number em Person".
  • Migração gerada é lida antes do commit, não só confiada ao autogenerate.
  • PR: make ready verde, migração revisada, screenshot se a mudança é visual.
  • Rota de escrita sem require_perm explícito e sem auditoria não passa em review.

A fonte normativa de tudo isso é o CLAUDE.md na raiz — que, apesar do nome, é o guia do projeto para humanos e agentes de código igualmente. Em conflito entre ele e o código, ele vence.
