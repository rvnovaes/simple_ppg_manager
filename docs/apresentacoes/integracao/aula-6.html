Aula 6 — Fluxo de entrega: Git, CI/CD e Ansible DRAFT

A aula 5 terminou com o trabalho pronto em uma branch isolada. Agora acompanhamos esse código até os ambientes de teste e produção: merge, push, build, testes e implantação automatizada. O Git não é um assunto paralelo — é o mecanismo que dispara e documenta a entrega.

Rascunho. A narrativa e o fluxo geral estão definidos. Antes de fechar a aula, ainda é preciso substituir os exemplos genéricos pelos nomes reais dos workflows, playbooks, inventários, ambientes e comandos adotados no projeto.

1

Da worktree à entrega

8 min

Nas aulas anteriores, o desenvolvimento termina em uma branch própria: humana ou produzida pelo Helton em uma worktree. Ela contém commits revisáveis e deve passar pelo mesmo critério local de sempre: make ready verde antes de sair da máquina.

A partir daqui muda a pergunta. Já não queremos saber apenas se a mudança funciona isoladamente; queremos saber se ela se integra ao restante do projeto e se pode ser instalada de modo reproduzível.

  • worktreedesenvolver, testar e commitar em isolamento
  • developintegrar mudanças e produzir o ambiente de teste
  • mainrepresentar o estado autorizado para produção

A ideia central. Branch não é ambiente, mas neste projeto uma branch protegida funciona como o contrato que autoriza a automação a atualizar determinado ambiente.

2

Branches como contrato de ambientes

10 min
BranchSignificadoPush dispara
branch de trabalhoMudança ainda isolada e revisávelNenhuma implantação
developConjunto integrado candidato à próxima entregaBuild, testes e atualização do ambiente de teste
mainEstado aprovado para uso produtivoBuild e implantação em produção

Esse desenho reduz o vocabulário: não existe um procedimento manual diferente para cada servidor. Existe uma promoção explícita no Git, e o pipeline traduz essa promoção em build, verificação e implantação.

O nome da branch produtiva deve ser uniforme em código, documentação e configuração. Este repositório usa main; qualquer referência antiga a master deve ser corrigida antes de finalizar a aula.

3

Merge e push em develop

12 min

O caminho normal integra a branch concluída em develop. O merge registra que duas linhas de trabalho se encontraram; o push entrega esse novo estado ao repositório remoto e aciona o pipeline.

git switch develop
git pull --ff-only origin develop

# branch criada na worktree ou no canteiro
git merge --no-ff helton/<nome-da-entrega>

make ready
git push origin develop

O segundo make ready não é repetição inútil. A branch de trabalho pode estar verde sozinha e, ainda assim, conflitar semanticamente com outra mudança que entrou em develop. O teste após o merge verifica o estado que será efetivamente enviado.

Push não é experimento. Se make ready falhou, não se envia para “ver o que o CI diz”. O CI repete o critério em ambiente limpo; ele não substitui a verificação local.

4

O pipeline de integração

15 min

Continuous Integration significa integrar mudanças frequentemente e provar, de forma automatizada, que o conjunto continua coerente. O gatilho é o push em develop; o valor está nas verificações que vêm depois.

  • checkoutobtém exatamente o commit enviado
  • buildmonta backend e frontend em ambiente limpo
  • qualityexecuta lint, typecheck e demais verificações estáticas
  • testroda a suíte automatizada contra os serviços necessários
  • artifactproduz ou identifica o artefato que será implantado
  • deploy-testchama a automação do ambiente de teste somente se tudo estiver verde

A ordem é uma barreira: a implantação não deve começar se build ou testes falharem. O commit permanece em develop, mas o ambiente conhecido como saudável não é substituído por uma entrega reprovada.

CI e CD não são a mesma coisa

Build e testes pertencem à integração contínua. Atualizar o ambiente de teste e, depois, a produção pertence à entrega ou implantação contínua. Por isso o título da aula fala em CI/CD: o Ansible entra principalmente depois que a integração foi validada.

5

O papel do Ansible

15 min

O pipeline decide quando uma implantação pode acontecer. O Ansible descreve como levar o servidor ao estado desejado: arquivos, serviços, variáveis, migrações e reinícios necessários.

PeçaResponsabilidade
Workflow do CI/CDGatilho, ordem das etapas, gates e associação entre branch e ambiente
InventárioQuais hosts pertencem a teste ou produção
PlaybookSequência declarativa para alcançar o estado desejado
RolesResponsabilidades reutilizáveis: aplicação, proxy, banco, observabilidade
SecretsCredenciais fornecidas fora do repositório e apenas ao ambiente autorizado

A propriedade essencial é a idempotência: executar o playbook duas vezes deve produzir o mesmo estado, não duplicar configuração nem acumular efeitos colaterais.

Separação de poderes. O pipeline não deve conter uma longa sequência de SSH improvisada, e o playbook não deve decidir qual branch merece produção. Cada peça mantém sua responsabilidade.

6

Promoção para produção

12 min

Depois que o commit foi validado em develop e observado no ambiente de teste, ele é promovido para main. Não se reconstrói a mudança nem se altera o código “na passagem”: promove-se o que já foi testado.

git switch main
git pull --ff-only origin main
git merge --no-ff develop
git push origin main

O push em main aciona o pipeline produtivo. Ele repete as verificações necessárias, identifica o commit promovido e chama o inventário/playbook de produção. A diferença entre teste e produção deve estar na configuração do ambiente, não em branches com código divergente.

Gate humano. Produção é uma decisão institucional. Definir se o merge exige pull request, aprovação, janela de implantação ou acionamento manual é parte da política do projeto e deve estar refletido nas proteções de branch — não apenas escrito nesta aula.

7

Falha, rollback e correção urgente

10 min

Automação segura não é a que nunca falha; é a que falha de modo visível, interrompe no ponto correto e preserva um caminho de recuperação.

FalhaResposta esperada
Build ou teste em developPipeline vermelho; nenhuma implantação; corrigir em nova branch
Ansible no ambiente de testeInterromper; examinar a tarefa e o host; corrigir o playbook antes de produção
Pipeline de mainBloquear a nova versão e preservar a última versão conhecida como saudável
Defeito descoberto após implantaçãoReverter para artefato/commit anterior ou produzir correção urgente pelo mesmo fluxo

Uma correção urgente não autoriza editar o servidor na mão. Ela encurta o tempo, não elimina rastreabilidade, testes e capacidade de repetir a implantação.

Decisão pendente do rascunho. Registrar o mecanismo real de rollback: imagem anterior, checkout de tag, reversão de commit, backup de banco e compatibilidade de migrações. Sem isso, “rollback” é apenas uma intenção.

8

Exercício e decisões pendentes

8 min

Exercício guiado

  1. Partir de uma branch de trabalho já aprovada.
  2. Integrá-la em develop e executar make ready.
  3. Fazer o push e acompanhar cada etapa do pipeline.
  4. Confirmar a versão no ambiente de teste.
  5. Simular uma falha controlada e identificar em qual gate ela é interrompida.
  6. Descrever, sem executar, a promoção do mesmo commit para main.

Para fechar esta aula

  • Inserir os nomes e caminhos reais dos workflows e playbooks.
  • Confirmar se produção usa main e remover referências a master.
  • Definir proteções e aprovações exigidas em develop e main.
  • Documentar onde ficam os logs do pipeline e do Ansible.
  • Escrever o procedimento testado de rollback.
  • Confirmar como migrações de banco são tratadas antes e durante a implantação.
