1

O que estamos construindo

10 min

O PPGM gerencia um programa de pós-graduação: pessoas, usuários, papéis, permissões e auditoria formam o primeiro módulo; a vida acadêmica (matrículas, disciplinas isoladas, editais) já cresce em cima dessa fundação. Foi criado para uma instituição, mas nasceu multi-tenant: quase toda tabela de negócio carrega uma chave para o programa, porque o sistema será usado por outros cursos.

Duas consequências práticas dessa decisão, que você vai encontrar no código desde o primeiro dia:

  • Toda consulta de dado de negócio é escopada por current_program(request) — nunca por um program_id que o chamador escolhe. Um filtro opcional vazaria o tenant inteiro para quem omitir o parâmetro.
  • A carga de demonstração (make seed) semeia dois programas de propósito: com um só, um vazamento entre tenants não aparece em teste nenhum.

Contexto do time. Somos fortes em infraestrutura e iniciantes em desenvolvimento. Por isso toda decisão do projeto favorece menos peças móveis e menos decisões em aberto — mesmo quando existe alternativa mais sofisticada. Essa frase explica quase tudo que vem a seguir.

Entendendo os "nãos"

A coluna da direita da tabela lista tecnologias populares — você vai vê-las em todo tutorial. Cada "não" daqui tem um mal concreto por trás, registrado em ADR. Vale a pena entender o que cada coisa é antes de entender por que a recusamos.

async

O que é: o modelo de concorrência cooperativa do Python (async def / await), em que uma única thread intercala muitas requisições — cada função "devolve o controle" enquanto espera I/O (banco, rede). É o modelo do FastAPI e o motivo da sua fama de rápido.

O mal de usar aqui: async cria uma classe inteira de bug que não existe no código síncrono — e são bugs traiçoeiros para quem está aprendendo. Um await esquecido não dá erro: devolve silenciosamente uma corrotina em vez do resultado. Uma consulta ao ORM feita no lugar errado explode com "objeto fora do event loop". Uma biblioteca síncrona no meio do caminho trava o loop inteiro — e nada disso quebra na hora: quebra sob carga, o pior formato possível de defeito. E o ganho seria zero: nosso pico são dezenas de usuários simultâneos, não milhares. O custo dominante do projeto é erro humano, não CPU (ADR-001). Se um dia houver gargalo real de I/O, mede-se primeiro; a saída provável é um worker em background, não reescrever tudo em async.

DRF e GraphQL

O que são: o Django REST Framework é a camada de API mais tradicional do mundo Django; GraphQL é um protocolo em que o cliente compõe a consulta que quiser, em vez de chamar endpoints fixos.

O mal de usar aqui: o DRF traz um vocabulário próprio inteiro — serializers, viewsets, routers, permission classes — que seria mais uma coisa a aprender além do Django. O Django Ninja usa o que o time já precisa saber para escrever Python moderno: type hints e classes Pydantic. E dá algo de graça que o DRF não dá: o schema OpenAPI, do qual o make gen-api gera os tipos TypeScript do front — o contrato entre back e front vira código verificável, não combinado verbal. GraphQL resolveria um problema que não temos (muitos clientes com necessidades de dados diferentes) ao preço de problemas novos: cache, autorização por campo, consultas N+1 montadas pelo cliente.

JWT

O que é: JSON Web Token — um "crachá" assinado que o servidor entrega no login e o cliente reapresenta em cada requisição, normalmente num header. O servidor não guarda nada: confia na assinatura. É o padrão quando API e front vivem em domínios diferentes, ou quando vários serviços consomem a mesma API.

O mal de usar aqui: não é o nosso caso — temos um front, na mesma origem que a API. Nesse cenário, JWT é um rebaixamento de segurança operacional em três frentes (ADR-003):

  • Onde guardar o token? O lugar usual é o localStorage — que qualquer JavaScript da página lê. Um único XSS (script injetado) rouba o token e vira roubo de conta. O cookie de sessão do Django é HttpOnly: o JavaScript simplesmente não o alcança.
  • Não dá para revogar. A graça do JWT é o servidor não guardar estado — mas então "deslogar" um usuário ou banir uma conta comprometida exige inventar uma denylist de tokens... que é reinventar a tabela de sessões, mal. Com sessão do Django, logout revoga no servidor, com efeito imediato.
  • Renovação é um segundo sistema. Token expira; para o usuário não ser deslogado a cada hora, escreve-se o fluxo de refresh token — mais código de segurança para nós mantermos. Tudo isso já vem pronto e testado no Django há vinte anos.

O preço que pagamos em troca: toda escrita precisa do header X-CSRFToken. Esse preço foi pago uma única vez, dentro de lib/api/client.ts — nenhuma tela lida com CSRF. Se um dia houver app móvel ou integração de terceiro, é ADR novo (provavelmente token de serviço com escopo, não JWT de usuário).

CORS

O que é: por padrão, o navegador impõe a same-origin policy: a página de uma origem (esquema + host + porta) não pode ler respostas de outra. CORS (Cross-Origin Resource Sharing) é o mecanismo de cabeçalhos HTTP que relaxa essa proteção — o servidor declara "aceito ser chamado pela origem X". É o que todo tutorial de SPA manda configurar quando o front roda na :5173 e a API na :8000.

O mal de usar aqui: CORS não é um recurso, é a desativação seletiva de uma proteção do navegador — e mal configurado é uma das fontes mais frequentes de brecha e de tempo perdido (ADR-004). Com cookie de sessão, piora: origem cruzada exige a tríade SameSite=None + Secure + credentials, e qualquer erro em uma das três quebra o login com mensagens enigmáticas do navegador. Nossa solução dissolve o problema em vez de gerenciá-lo: front e API atrás do mesmo Nginx, na mesma origem — não há "cross-origin", logo não há o que configurar. E isso é literalmente uma configuração de Nginx, o problema que este time já sabe resolver melhor que ninguém. Daí a regra de review: se você sentiu necessidade de CORS, o erro está no deploy, não no código. O bloco 4 mostra como o Nginx faz isso na prática.

SSR e Node em produção

O que é: Server-Side Rendering — em vez de o navegador montar a página com JavaScript, um processo Node monta o HTML no servidor a cada requisição. No SvelteKit, é o modo do adapter-node.

O mal de usar aqui: SSR entrega SEO e primeiro carregamento mais rápido — dois benefícios que valem zero num sistema atrás de login, não indexável, usado por público interno em rede boa. O custo, porém, seria permanente e cai em cima da infra: um segundo runtime (Node além do Python) para instalar, supervisionar, monitorar, atualizar e incluir no plano de recuperação (ADR-005). Com adapter-static, o deploy do front é copiar arquivos, e o rollback é copiar os arquivos anteriores — não há processo para reiniciar nem porta para vigiar. Produção inteira são três peças que já operamos: Nginx, gunicorn, Postgres.

SQLite fora de teste local

O que é: um banco embutido num arquivo, sem servidor — ótimo para protótipo.

O mal de usar aqui: paridade. SQLite e Postgres divergem em tipos, constraints e comportamento de transação; um teste que passa no SQLite pode quebrar no Postgres de produção — e você só descobre em produção. Por isso a suíte de testes roda contra Postgres de verdade (o do make db).

pip/poetry, yarn/pnpm

O mal aqui é mais brando, mas real: cada gerenciador extra é um lockfile com formato próprio e um comando a mais para errar. Uma ferramenta por ecossistema — uv no Python, npm no Node — e instalação sempre reprodutível (uv sync --locked, npm ci). Duas pessoas com lockfiles diferentes é o "funciona na minha máquina" nascendo.

O padrão que une todos os nãos: nenhuma dessas tecnologias é ruim em si — JWT, CORS, async e SSR existem para problemas reais. Só que são problemas que não temos: múltiplas origens, múltiplos clientes, milhares de usuários, SEO. Adotá-las importaria os custos (bugs sob carga, tokens roubáveis, proteção de navegador desligada, um runtime a mais) sem importar benefício nenhum. Complexidade só entra aqui pagando com um caso de uso presente — é a regra da Seção 12 do CLAUDE.md.

E uma regra de acesso que confunde todo novato: o Django Admin é só para sysadmin (ADR-006). Usuário de negócio — secretaria, coordenação, docente — usa tela Svelte, sempre. O Admin serve para criar programas, ler auditoria e corrigir dado em modo quebra-vidro. Se falta uma tela, o trabalho é escrever a tela, nunca "manda usar o Admin".

Anatomia do docker-compose

25 min

Este é o coração da aula, porque é o território de vocês. O docker-compose.yml sobe quatro serviços, e cada linha incomum dele tem uma história — o próprio arquivo é comentado, leia-o inteiro depois.

Serviço a serviço

ServiçoImagemPorta no hostO que importa saber
dbpostgres:17.5-alpine5433Volume nomeado pgdata; healthcheck com pg_isready segura o backend até o banco aceitar conexão
backendbuild de ./backendnenhumarunserver com o código montado como volume — editar no host recarrega no container
frontendnode:25-slimnenhumaVite dev server, só existe em dev; em produção o Nginx serve o build estático
nginxnginx:alpine8080A única porta de entrada; config montada de nginx/

As cinco linhas que têm história

name: simple_ppg_manager cravado. Sem isso o Compose deriva o nome do projeto do nome da pasta — e renomear o diretório criaria um projeto novo com volume vazio, "perdendo" o banco sem apagar nada.

Postgres na 5433, não 5432. A 5432 desta máquina já pertence a outro projeto. E atenção de infra: trocar a major do Postgres (17 → 18) invalida o data dir do volume. O caminho é pg_dump, recriar o volume, restaurar — nunca só trocar a tag da imagem.

O Vite roda dentro do Compose, não no host. Antes ele rodava no host e o Nginx o alcançava por host.docker.internal. Com worktrees paralelas isso quebrou de um jeito silencioso: N stacks apontavam todas para o mesmo Vite, e cada uma exibia o front de outra worktree, sem erro nenhum na tela. Agora a 5173 é um endereço interno da rede de cada stack — N stacks rodam N Vites sem combinar porta nenhuma.

node:25-slim, jamais -alpine. O node_modules montado no container é o mesmo do host, e o npm ci baixa binários linux-x64-gnu (glibc) do rollup e do Tailwind. Numa imagem musl eles não carregam — e o erro aparece como cannot find module de um pacote que está visivelmente lá.

Portas parametrizadas (NGINX_PORT, DB_PORT). Porta cravada colide quando duas stacks do projeto rodam no mesmo host — é o que permite os "canteiros" (worktrees com stack própria) da esteira autônoma. No dia a dia os defaults 8080/5433 valem.

Origem única: o Nginx é o produto

10 min

Front e API atendem no mesmo host e porta. Não é conveniência — é o que faz autenticação funcionar: o cookie de sessão e o CSRF do Django só se comportam quando o navegador enxerga uma origem só. Por isso o projeto nunca configura CORS; sentir necessidade de CORS significa que o deploy está errado, não o código (ADR-004).

RotaVai paraConteúdo
/api/DjangoAPI Ninja (/api sozinho redireciona para /api/v1/docs)
/admin/DjangoAdmin, restrito a superusuário
/static/ /media/DjangoCSS do Admin e uploads
/Vite (dev)A SPA, com hot reload via WebSocket. Em produção, este bloco vira root + try_files servindo o build estático

Regra de ouro: sempre :8080. Abrir a porta do Vite direto quebra login e CSRF. Hoje isso é difícil de fazer por acidente — a 5173 nem é publicada no host — mas a regra vale para qualquer arranjo futuro.

Produção é o mesmo desenho sem o Vite: um Nginx com TLS, um gunicorn, um Postgres. Nenhum processo Node, em nenhuma hipótese.

5

Mão na massa: subir a stack

15 min

Cada um faz agora no próprio notebook. Pré-requisitos: Docker, uv e Node instalados.

git clone https://github.com/rvnovaes/simple_ppg_manager.git
cd simple_ppg_manager
cp .env.example .env              # ajuste se precisar
cd frontend && npm ci && cd ..    # ci, não install: preserva o lockfile
cd backend  && uv sync --locked && cd ..
make up                           # sobe os quatro serviços
make migrate && make seed         # migra e carrega dados de demonstração

Por que npm ci e uv sync --locked, e não npm install / uv sync

Os dois instalam exatamente as versões gravadas nos lockfiles (package-lock.json e uv.lock) — todo mundo, e a produção, com byte a byte as mesmas dependências. As variantes sem trava fazem outra coisa: resolvem versões de novo e reescrevem o lockfile, o que muda a árvore do git sem você ter pedido nada e abre a porta do "funciona na minha máquina". Um detalhe a mais neste projeto: o node_modules que esse npm ci cria no host é o mesmo que o Compose monta dentro do serviço frontend — outro motivo da imagem node:25-slim (glibc) do bloco 3.

Regra prática: instalar é sempre npm ci / uv sync --locked. npm install <pacote> e uv add <pacote> só quando se está deliberadamente adicionando ou atualizando uma dependência — aí a mudança do lockfile é intencional e vai revisada no commit.

Abra http://localhost:8080. As contas de teste estão em CONTAS-DEMO.txt na raiz — o login é o e-mail completo, e a senha é a mesma para todas. O seed é idempotente e cria dois programas (lembra do bloco 1?).

Comandos do dia a dia

Tudo passa pelo Makefile — make sem argumento lista os alvos. Os que você vai usar toda hora:

ComandoO que faz
make up / make downSobe e derruba a stack (o down preserva o volume do banco)
make webAcompanha o log do Vite (que já sobe com o make up)
make migrations / migrateGera e aplica migrações — rodam no host, via uv, contra a 5433
make gen-apiRegenera os tipos TS do front a partir do OpenAPI — sempre que mexer em schema ou rota
make readylint + typecheck + testes. Verde é pré-condição de commit
6

Armadilhas já pagas

5 min

Cada uma destas custou horas de alguém. Estão documentadas no manual_dev.md; aqui vão as que pegam um novato na primeira semana:

O front carrega mas não atualiza ao salvar. O hmr.clientPort do Vite precisa da porta publicada do Nginx (ele lê NGINX_PORT). Se divergirem, o hot reload morre em silêncio — nada na tela acusa.

cannot find module de um pacote que está no node_modules. Alguém trocou a imagem para musl (-alpine). Os binários são glibc; a imagem é -slim de propósito.

Login devolve 403 sem explicação. CSRF_TRUSTED_ORIGINS não bate com a porta do Nginx. A mensagem de erro não menciona porta nenhuma.

npm install ou uv sync sem --locked. Reescrevem o lockfile e sujam a árvore. Instalação é sempre npm ci e uv sync --locked.
